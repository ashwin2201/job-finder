# JobNavi Japan

JobNavi Japan is a full-stack job discovery and career-management application for candidates and employers in Japan. It combines a Next.js frontend with a FastAPI/PostgreSQL backend, Clerk authentication, role-based company management, job matching, and AI-assisted Japanese resume generation.

## Features

### Candidates

- Search and filter published jobs with backend pagination
- Save jobs and track submitted applications
- Maintain multiple resumes and select one primary resume
- Generate resume feedback and refresh ranked job matches
- View profile-view statistics
- Start direct conversations and exchange messages
- Generate a Japanese resume tailored to a target job description

### Employers

- Create companies and manage company memberships
- Assign owner, admin, recruiter, and member roles
- Create, edit, publish, and close job postings
- Review applications and update application statuses

### Platform

- Clerk JWT authentication and signed webhook provisioning
- PostgreSQL persistence through SQLModel and SQLAlchemy
- TF-IDF and cosine-similarity job matching
- RAG-style resume generation using OpenAI embeddings, PGVector, and the OpenAI Responses API
- Interactive OpenAPI documentation generated by FastAPI

## Architecture

```text
frontend/src/
├── app/                 Next.js routes and layouts
├── features/            Feature-owned screens, components, hooks, and API clients
├── components/          Shared UI and layout components
├── lib/                 Shared utilities
└── types/               Shared TypeScript contracts

backend/app/
├── api/routes/          FastAPI controllers and dependency wiring
├── core/                Configuration, database, CORS, and authentication
├── models/              SQLModel database tables and relationships
├── schemas/             Request and response validation models
├── services/            Business logic and database queries
└── integrations/        Scraping, job matching, and resume-generation adapters
```

The frontend follows feature boundaries enforced by `frontend/independentModules.jsonc`. Features may use their own modules and shared code, but they may not import implementation details from other features.

Backend routes remain thin: they validate HTTP input and authorization, then delegate persistence and business behavior to the service layer.

## Local Setup

### 1. Clone the repository

```bash
git clone https://github.com/ashwin2201/job-finder.git
cd job-finder
```

### 2. Configure PostgreSQL

Create a database, for example:

```sql
CREATE DATABASE job_finder;
```

For AI resume retrieval, enable PGVector in that database:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

### 3. Configure and run the backend

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Add the database connection to `backend/.env` and complete the Clerk/OpenAI values:

```env
PG_CONN=postgresql+psycopg://postgres:postgres@localhost:5432/job_finder
FRONTEND_ORIGIN=http://localhost:3000

CLERK_ISSUER=https://your-instance.clerk.accounts.dev
CLERK_AUDIENCE=
CLERK_AUTHORIZED_PARTY=http://localhost:3000
CLERK_WEBHOOK_SECRET=whsec_your_webhook_secret

OPENAI_API_KEY=your_openai_api_key
OPENAI_MODEL=gpt-5.4
```

Start FastAPI from the `backend` directory:

```bash
PYTHONPATH=app uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

On startup, SQLModel creates tables that do not exist and seeds jobs when the jobs table is empty.

### 4. Configure and run the frontend

In another terminal:

```bash
cd frontend
npm install
```

Create `frontend/.env.local`:

```env
NEXT_PUBLIC_API_URL=http://localhost:8000/api
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=your_clerk_publishable_key
CLERK_SECRET_KEY=your_clerk_secret_key
```

Start Next.js:

```bash
npm run dev
```

Open the services at:

- Frontend: <http://localhost:3000>
- Backend: <http://localhost:8000>
- Swagger UI: <http://localhost:8000/docs>
- OpenAPI JSON: <http://localhost:8000/openapi.json>

## Clerk Provisioning

Authenticated backend routes expect every Clerk account to have corresponding rows in `users` and `auth_identities`. Configure a Clerk webhook that sends `user.created`, `user.updated`, and `user.deleted` events to:

```text
POST https://your-public-backend.example/api/webhooks/clerk
```

Clerk cannot call `localhost` directly. During local development, expose port `8000` with a tunnel and use its HTTPS URL for the webhook endpoint. Put the webhook signing secret in `CLERK_WEBHOOK_SECRET`.

For a Clerk account created before the webhook was configured, resend a user event from Clerk or update the account so the backend can provision it.

## Existing Database Migrations

`SQLModel.metadata.create_all()` creates missing tables, but it does not alter tables that already exist. Apply the SQL migrations in chronological order when upgrading an existing database:

```bash
cd backend
psql postgresql://postgres:postgres@localhost:5432/job_finder \
  -f migrations/20260628_add_company_status.sql
psql postgresql://postgres:postgres@localhost:5432/job_finder \
  -f migrations/20260728_add_application_features.sql
```

Back up databases containing important data before applying schema changes.

## AI Resume Generation

The generation endpoint accepts a candidate's existing resume, personal details, and a target job description:

```text
POST /api/generate-resume
```

The pipeline:

1. Embeds the target job description.
2. Retrieves five relevant Japanese resume snippets from the `jp_snippets` PGVector collection.
3. Sends the candidate data, job description, and retrieved context to OpenAI.
4. Runs a second model pass to correct keigo and casual phrasing.
5. Stores the source submission and generated Japanese resume in PostgreSQL.

The reference documents can be ingested from `backend/app/integrations/resume_generator/raw_docs`:

```bash
cd backend/app/integrations/resume_generator
PYTHONPATH=../.. python docs_ingest.py
```

AI-generated resumes currently use the legacy `ResumeSubmission` and `GeneratedResume` tables. Authenticated resume management and feedback use the separate `UserResume` and `ResumeFeedback` tables.

## API Overview

| Domain | Main routes |
| --- | --- |
| Public jobs | `GET /api/jobs`, `GET /api/jobs/{job_id}` |
| Identity | `/api/me`, `/api/me/profile`, `/api/me/companies` |
| Companies | `/api/companies`, `/api/companies/{company_id}/members` |
| Employer jobs | `/api/companies/{company_id}/jobs` |
| Applications | `/api/jobs/{job_id}/applications`, `/api/me/applications`, `/api/companies/{company_id}/applications` |
| Saved and matched jobs | `/api/me/saved-jobs`, `/api/me/job-matches` |
| User resumes | `/api/me/resumes`, `/api/me/resumes/{resume_id}/feedback` |
| Profiles | `/api/users/{user_id}`, `/api/me/profile-views` |
| Messaging | `/api/conversations`, `/api/conversations/{conversation_id}/messages` |
| AI resume generation | `/api/submit-resume`, `/api/generate-resume` |
| Clerk webhook | `POST /api/webhooks/clerk` |

Use Swagger UI for complete request schemas, response schemas, filters, and status codes.

## Job Filtering and Pagination

`GET /api/jobs` supports `q`, `company`, repeated `work_styles`, repeated `languages`, `visa_support`, `page`, and `page_size` query parameters. Filtering and the total count are calculated in PostgreSQL before pagination, so the returned `total` and `total_pages` describe the filtered result set.
